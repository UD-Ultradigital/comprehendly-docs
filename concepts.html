Concepts

Page vs submission

A published form page is the schema you load with page.get(pageId). A submission is saved data for that page. The submission payload is keyed by field_name, not labels.

Field identity

Key Use
element.id Stable page node id. Preferred key for binding host widgets.
field_name Engine and submission key. Use it for voice patches, store values, and save payloads.
Label text Display only. Never bind or save by label.

Reload the mapping after every page.get. The SDK store handles this for bind({ elementId }) so host code can stay on stable element ids.

FieldStore

Each fill session uses one FieldStore. Generated controls, bound controls, and voice patches all write into the same store so save always reads a single source of truth.

Fillable elements are form_field, form_field_rating, and form_field_score. Generated UI in v1 only renders primitive form_field input types; other fillable elements still appear in the store.

Surfaces

Surface Who renders it Best for
Generated FormView SDK Fast starts where a linear list of primitive controls is acceptable.
Bound Your app Existing or branded widgets mapped from element.id.

Choose generated UI or bind for each field. Do not overlay Comprehendly chrome on top of existing widgets.

Voice

Voice capture stays on the hosted voice-bridge.html page and the forms fill embed. SDKs mint voice sessions with forms.voice.start, then pass the short-lived token into the hosted bridge instead of reimplementing the Realtime client.

Forms embed v1.3 posts stepcare:fields_updated as values change and stepcare:submission_saved when the hosted flow saves.
